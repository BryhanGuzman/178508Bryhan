INFORMACIÓN GENERAL

Sobre el laboratorio

El laboratorio demuestra cómo una validación aparentemente correcta puede ser evadida cuando el servidor procesa y decodifica la entrada del usuario después de aplicar sus filtros de seguridad.

La aplicación utiliza nombres de archivos proporcionados mediante una solicitud HTTP para construir rutas dentro del sistema de archivos. Aunque intenta eliminar las secuencias tradicionales de salto de directorio, existe un problema en el orden en que se realizan la validación y la decodificación URL.

ANÁLISIS TÉCNICO

¿Dónde está la vulnerabilidad?

El problema no es únicamente el filtro.

La vulnerabilidad ocurre cuando la aplicación utiliza entradas proporcionadas por el usuario para construir rutas de acceso a archivos sin realizar una validación y sanitización adecuada.

El servidor intenta protegerse filtrando secuencias conocidas de navegación entre directorios, como ../ o %2f. Sin embargo, posteriormente realiza otra operación de URL-decode.

Esto provoca una falla en el orden de procesamiento: una cadena que inicialmente parece segura puede convertirse en una secuencia de Path Traversal después de ser decodificada.

PROCEDIMIENTO

Desarrollo del laboratorio

El laboratorio se realizó utilizando PortSwigger Web Security Academy y Burp Suite. El procedimiento consistió en interceptar la solicitud encargada de recuperar una imagen, enviarla a Repeater y modificar el parámetro filename.

01
ACCESO

Iniciar el laboratorio

Se accede al laboratorio File path traversal, traversal sequences stripped with superfluous URL-decode y se selecciona la opción ACCESS THE LAB.

02
BURP SUITE

Preparar el proxy

Se inicia Burp Suite utilizando un proyecto temporal y la configuración predeterminada. Desde la pestaña Proxy se abre el navegador integrado para acceder al laboratorio.

03
INTERCEPT

Localizar la solicitud

Al navegar por la aplicación se identifica la solicitud:

GET /image?filename=70.jpg HTTP/2

Esta petición utiliza el parámetro filename para indicar el archivo que debe recuperar el servidor.

04
REPEATER

Enviar la solicitud a Repeater

La solicitud HTTP correspondiente a la imagen se selecciona y se utiliza la opción Send to Repeater para poder modificarla y enviarla manualmente.

05
EXPLOTACIÓN

Sustituir el nombre del archivo

Dentro de Repeater se sustituye 70.jpg por el payload:

..%252f..%252f..%252fetc/passwd

Posteriormente se presiona Send para enviar la solicitud modificada al servidor.

La respuesta del servidor muestra el contenido del archivo solicitado, confirmando que la secuencia doblemente codificada logró evadir el filtro de la aplicación.

05
DEFENSA

Mitigaciones recomendadas

01

Evitar rutas del usuario

Evitar utilizar directamente nombres o rutas de archivos enviados desde el cliente. Es preferible utilizar identificadores asociados a una lista de archivos permitidos.

02

Decodificar primero

Cualquier proceso de URL-decode debe realizarse antes de aplicar las reglas de validación y sanitización sobre la entrada recibida.

03

Canonicalización

Resolver la ruta absoluta del archivo y comprobar que permanezca dentro del directorio autorizado para los recursos públicos.

04

Mínimo privilegio

El proceso del servidor web debe ejecutarse con permisos restringidos para evitar que pueda leer archivos sensibles del sistema operativo.

CONCLUSIÓN

La codificación no sustituye a la validación.

Este laboratorio permitió observar cómo una aplicación puede seguir siendo vulnerable a File Path Traversal incluso cuando intenta eliminar secuencias peligrosas. El problema aparece cuando la validación se realiza antes de completar todas las transformaciones de la entrada.

Mediante doble codificación URL fue posible ocultar temporalmente la secuencia de traversal, superar el filtro inicial y conseguir que el servidor reconstruyera posteriormente una ruta válida hacia /etc/passwd.
